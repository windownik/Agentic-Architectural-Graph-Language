# Техническая спецификация AAGL — Слой контейнера

**Версия стандарта:** 0.1.0  
**Статус:** Черновик / Спецификация системы хранения  
**Область применения:** Этот документ определяет ИСКЛЮЧИТЕЛЬНО физическую структуру файлов, маршрутизацию, хэширование, разбиение на чанки, инварианты структуры графа, механику мутаций и МЕХАНИЗМ разрешения представлений (view) для контейнерного формата `.aagl`. Он явно **не** определяет:
- Какие семантические «типы» может иметь узел;
- Какие ключи должен или может содержать объект `metadata` узла;
- Какие ключи может принимать правило стиля или что эти ключи означают для рендерера.

Эти вопросы относятся к **профилю** (также называемому *протоколом* или *доменной схемой*), на который ссылается файл `manifest.json`. Несколько более высокоуровневых протоколов (архитектурные планы этажей, разводка печатных плат, сетевые топологии, механические сборки и т. д.) могут использовать этот единый формат контейнера, подключая различные определения профилей.

---

## 1. Обзор и цели

**AAGL (Agentic Architectural Graph Language)** — это встраиваемый высокопроизводительный движок хранения пространственных графов, реализованный на Rust. Он хранит, запрашивает и изменяет сложные пространственные/структурные графы детерминированным образом с семантикой контроля версий, оптимизированной для параллельных автономных ИИ-агентов.

Два не подлежащих обсуждению принципа разделения уровней:
1. **Разделение формата и протокола.** Контейнерный формат (данный документ) не знает о типах. Семантические контракты для словарей полей `metadata` и в стиле `view` декларируются в **профиле**, выбранном автором, и маршрутизируются через `manifest.profile`.
2. **Разделение данных и представлений.** Все файлы в директории `chunks/` содержат модель графа и ничего больше. Все стратегии презентации находятся в `views/` и являются непрозрачными (opaque) для базового движка. Косметические правки никогда не должны портить хэши данных или вызывать конфликты OCC (оптимистичного контроля параллелизма).

---

## 2. Формат контейнера (`.aagl`)

Проект AAGL представляет собой единый переносимый файл с расширением `.aagl`. Внутри это стандартный **ZIP-архив**; ридеры ДОЛЖНЫ использовать Центральный каталог ZIP (Central Directory) для O(1) быстрого произвольного доступа к отдельным файлам без стриминга всего архива целиком.

### Структура директорий (обязательная)
```text
project.aagl (ZIP)
├── manifest.json             # Таблица маршрутизации + якоря версий + объявление профиля (ОБЯЗАТЕЛЬНО)
├── schema.json               # Правила валидации узлов/метаданных профиля (ОБЯЗАТЕЛЬНО, непрозрачно для ядра)
├── chunks/                   # Шардированные подграфы — ТОЛЬКО данные графа (ОБЯЗАТЕЛЬНО, минимум один)
│   └── chunk_genesis.json    # Обязательный корневой чанк идентичности (ОБЯЗАТЕЛЬНО)
├── views/                    # Стратегии презентации — НИКОГДА не изменяют данные графа (ОПЦИОНАЛЬНО)
│   └── <theme_id>.json       # Каждая тема — отдельный файл
└── assets/                   # Бинарные вложения (текстуры, облака точек, растры) (ОПЦИОНАЛЬНО)
    └── ...

```

> **Инвариант:** Ничто в `chunks/` не имеет права ссылаться на данные представлений или встраивать их. Ничто в `views/` не имеет права дублировать или переопределять любые из четырех структурных полей узла (`parent_id`, `coords`, `relations`, `metadata`).

## 3. Глобальный манифест (`manifest.json`)

`manifest.json` — это авторитетный каталог для всего контейнера. Каждое поле в этом разделе является частью контракта уровня контейнера (и поэтому известно ядру Rust). Семантические поля — все, что касается типов узлов, словарей стилей, интерпретаций макета координат — живут внутри `manifest.profile` и обрабатываются базовым движком как непрозрачный блок (opaque blob).

```json
{
  "spec_version": "0.1.0",
  "project_name": "sample_project",
  "state_hash": "sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "global_version": 12,
  "profile": {
    "id": "my_domain_protocol_v3",
    "schema_path": "./schema.json",
    "view_type_key": "metadata.profile_key",
    "view_style_schema": {
      "_comment": "Непрозрачный контракт, определяемый профилем, описывающий ключи стилей, которые рендерер должен ожидать в by_type/by_id/fallback. Слой контейнера не парсит это — он лишь хранит и хэширует."
    },
    "core_hints": {
      "relation_codes": ["directed", "symmetric", "control", "dependent"],
      "coords_layout_registry": {
        "_comment": "Непрозрачно для ядра; используется валидаторами уровня профиля для назначения семантической интерпретации целочисленному массиву coords для каждого узла."
      }
    },
    "extensions": {}
  },
  "units": {
    "base_unit": "mm",
    "internal_resolution_to_meters": 0.001
  },
  "chunks": {
    "chunk_genesis": {
      "path": "./chunks/chunk_genesis.json",
      "hash": "sha256:def456...",
      "version": 1
    },
    "sector_01": {
      "path": "./chunks/sector_01.json",
      "hash": "sha256:abc123...",
      "version": 5
    }
  },
  "views": {
    "active_theme": "default_minimal",
    "registered": {
      "default_minimal": {
        "path": "./views/default_theme.json",
        "hash": "sha256:7a9f3e...",
        "version": 2
      }
    }
  },
  "spatial_index": {
    "node_0001": "chunk_genesis",
    "node_0002": "chunk_genesis"
  }
}


### 3.1 `manifest.profile` — где сосредоточены ВСЕ знания о типах и стилях

Это единая точка настройки, определяемая автором, которая отвечает на все семантические вопросы о проекте. Сам формат контейнера AAGL ничего из этого не знает.

| Поле | Тип | Значение (принадлежит профилю — ядро рассматривает как непрозрачный блок, за исключением маршрутизации путей) |
| --- | --- | --- |
| `id` | string | Стабильный идентификатор используемого высокоуровневого протокола, например `arch_floorplan_v2`, `pcb_oenull_v1`, `generic_spatial_v0`. Читатели могут при необходимости найти определение протокола за пределами контейнера. |
| `schema_path` | string | Путь (внутри ZIP) к файлу JSON Schema, принадлежащему профилю и проверяющему форму узлов, содержимое `metadata`, правила макета `coords`, разрешенные `relations` — все семантические аспекты. Само ядро Rust **не** запускает эту схему; это делает загрузчик профиля. |
| `view_type_key` | string | **Какой путь через точку (dotted path) в узле предоставляет дискриминатор, используемый в качестве ключа в `views/<theme>.json#/by_type`.** Пример: `"metadata.profile_key"` означает `by_type[node.metadata.profile_key]`. Делая это настраиваемым в манифесте, формат контейнера не зашивает жестко имя поля `type` — протоколы могут использовать `"class"`, `"kind"`, `"layer_code"`, составные дискриминаторы и т. д. |
| `view_style_schema` | object | Контракт, определяемый профилем, описывающий *какие ключи может содержать объект правила стиля* и их семантику (форматы цветов, коды штриховок, перечисления размещения меток, подсказки рендерера). Слой контейнера никогда не читает это; данные обрабатываются только рендерерами/загрузчиками профилей. |
| `core_hints` | object | Узкий, опциональный набор переопределений, которые ядро контейнера МОЖЕТ читать, если они присутствуют. В настоящее время стандартизован только `relation_codes` (список разрешенных строк `rel_type`; по умолчанию `[directed,symmetric,control,dependent]`, если отсутствует). |
| `extensions` | object | Свободный контейнер для будущих настроек уровня профиля без нарушения структуры контейнера. Ядро ДОЛЖНО игнорировать все, что находится в этом объекте. |

### 3.2 Хэш состояния / Якорь OCC

При вычислении `state_hash` само поле `state_hash` ДОЛЖНО быть временно установлено в `""` (или опущено) перед хэшированием, после чего полученный дайджест записывается обратно согласно правилу:

```
temp = manifest.clone();
temp.state_hash = "";
digest = sha256(canonical_json(temp));
manifest.state_hash = "sha256:" + hex(digest);

```

### 3.3 Регистрация представлений (View)

* Записи в `manifest.views.registered` используют ту же тройку `{path, hash, version}`, что и чанки, для согласованности учета.
* **Изменения версий представлений НЕ увеличивают `manifest.global_version` и НЕ изменяют `State_hash`.** Это необходимо для того, чтобы правки тем (подсветка выбора, смена акцентов, печать против экрана) не инвалидировали текущие параллельные OCC-записи в граф данных.
* `active_theme` — это подсказка для рендерера. Ядро никогда не читает, не принуждает и не изменяет ее.

## 4. Система координат (уровень контейнера)

* Массивы `coords` в каждом узле ДОЛЖНЫ содержать только нативные 64-битные знакомые целые числа (`i64`). Значения с плавающей точкой запрещены где бы то ни было в массиве `coords` на уровне контейнера (профили, разумеется, МОЖГУТ встраивать метаданные с плавающей точкой *внутри* объекта `metadata`, если того требует сценарий использования).
* Семантика глобального масштаба/единиц измерения объявляется в `manifest.units` и в остальном непрозрачна для ядра.

## 5. Чанки (`chunks/*.json`)

### 5.1 Гранулярность и изоляция

* Данные разбиваются на чанки целевым размером 50–100 КБ каждый.
* Каждый чанк представляет собой независимый подграф с внутренним деревом `parent_id` и перекрестными указателями через `relations`.
* Каждый JSON чанка имеет ровно три структурных поля верхнего уровня: `chunk_id` (строка, совпадает с ключом в манифесте), `version` (монотонное целое число $\ge$ 1) и `nodes` (объект `node_id → node`). Поле `bounds` (6-элементный массив `i64` вида `[x_min,y_min,z_min,x_max,y_max,z_max]`) является ОПЦИОНАЛЬНЫМ для любого чанка, но ОБЯЗАТЕЛЬНЫМ для `chunk_genesis` (см. 5.2).

### 5.2 Корневой чанк (Genesis Chunk)

* Каждый проект должен содержать ровно один чанк, зарегистрированный под идентификатором `chunk_genesis` по пути `./chunks/chunk_genesis.json`.
* Он ДОЛЖЕН объявлять 6-элементное поле `bounds`, определяющее глобальную пространственную оболочку проекта.
* Он ДОЛЖЕН содержать хотя бы один корневой узел, у которого `parent_id` равен буквальной строке `"genesis"`.
* Идентификатор `chunk_id` этого чанка неизменяем: его нельзя удалить, переименовать или отменить его регистрацию в `manifest.chunks` (хотя содержимое его `nodes` может развиваться).

### 5.3 Контракт узла (уровень контейнера — только четыре обязательных ключа)

Каждый узел, независимо от профиля, ДОЛЖЕН предоставлять ровно четыре обязательных структурных поля. **Эти четыре поля (и только они) известны ядру Rust.** Любые другие ключи верхнего уровня в узле являются расширениями, определяемыми профилем, и ДОЛЖНЫ игнорироваться ядром.

| Поле | Тип | Семантика уровня контейнера (слепа к профилю) |
| --- | --- | --- |
| `parent_id` | `String` | Указатель иерархического владения. Корневые узлы используют буквальную строку `"genesis"` (**никогда** `null`). Ядро обходит это дерево для каскадного удаления. Семантический «смысл» определяется профилем. |
| `coords` | `Vec<i64>` | Плоский массив 64-битных целых чисел со знаком. Ядро обрабатывает его как непрозрачный блок с сохранением порядка. Длина, макет и интерпретация определяются исключительно через `manifest.profile`. |
| `relations` | `Vec<Relation>` | Плоский массив межсетевых связей. См. 5.4. Ядро обеспечивает соблюдение только структурных инвариантов записей связей, но не их семантики. |
| `metadata` | `JSON Object` | Полностью непрозрачный объект, принадлежащий профилю. **Слой контейнера требует ноль ключей и запрещает ноль ключей здесь.** Все правила формы (требование поля-дискриминатора, принудительное соблюдение типов полей, даже запрет визуальных ключей в метаданных — если профиль решит так сделать) исходят из `manifest.profile.schema_path`. |

> **Не требуется зашитого в код поля `type`.** Контейнеру не нужно, чтобы узел содержал ключ `metadata.type`. То, где карта `by_type` слоя представлений ищет свой дискриминатор, полностью определяется путем через точку в `manifest.profile.view_type_key`.

### 5.4 Контракт связей (уровень контейнера — только три обязательных ключа)

Каждая запись в `relations` ДОЛЖНА иметь ровно эти три поля. Их семантика определяется профилем; ядро проверяет только структурное наличие и может осуществлять маршрутизацию через `target_chunk`.

| Поле | Тип | Значение на уровне контейнера |
| --- | --- | --- |
| `target` | `String` | `node_id` пункта назначения. |
| `target_chunk` | `String` | `chunk_id`, содержащий пункт назначения — обеспечивает межчаночную маршрутизацию через `manifest.spatial_index`. |
| `rel_type` | `String` | Один из разрешенного набора кодов. Набор контейнера по умолчанию: `["directed", "symmetric", "control", "dependent"]`, но профиль может переопределить этот список, установив `manifest.profile.core_hints.relation_codes` в другой массив строк. |

### 5.5 Эталонный (слепой к профилю) корневой чанк (Genesis Chunk)

```json
{
  "chunk_id": "chunk_genesis",
  "version": 1,
  "bounds": [0, 0, 0, 10000, 5000, 3000],
  "nodes": {
    "node_0001": {
      "parent_id": "genesis",
      "coords": [0, 0, 0, 10000, 5000, 3000],
      "relations": [],
      "metadata": {
        "profile_key": "container_root",
        "label": "Global Envelope",
        "custom": { "foo": "bar" }
      }
    },
    "node_0002": {
      "parent_id": "node_0001",
      "coords": [100, 200, 0, 1100, 200, 0, 1100, 200, 2800, 100, 200, 2800],
      "relations": [
        { "target": "node_0009", "target_chunk": "sector_02", "rel_type": "dependent" },
        { "target": "node_0003", "target_chunk": "chunk_genesis", "rel_type": "symmetric" },
        { "target": "node_0042", "target_chunk": "sector_02", "rel_type": "control" },
        { "target": "node_0017", "target_chunk": "sector_01", "rel_type": "directed" }
      ],
      "metadata": {
        "profile_key": "linear_feature_A",
        "props": { "p1": 200, "p2": "sample" }
      }
    }
  }
}

```

Обратите внимание: здесь нет никаких упоминаний `Wall`, `Door`, `fill_color`, `hatch`. Они не являются частью формата контейнера.

## 6. Оптимистичное управление конкрентностью (OCC) — Слой контейнера

1. Каждая запись ядра предоставляет `base_version` / `base_chunk_hash`, на базе которых она была построена.
2. Ядро сравнивает переданные значения с текущими якорями манифеста/чанка.
3. При совпадении → мутация применяется атомарно, `version` чанка / `manifest.global_version` инкрементируются, `state_hash` пересчитывается.
4. При несоответствии → транзакция отклоняется; вызывающий код должен выполнить ребазирование (rebase).
5. Правки тем представлений (внутри `views/`) **исключены** из обнаружения OCC-конфликтов в графе данных: рендереры заменяют их свободно и обновляют `manifest.views.registered[theme_id].{hash,version}` без затрагивания `global_version` или `state_hash`.

---

## 7. Протокол мутаций: JSON Patch

Мутации графа данных применяются в виде атомарных последовательностей JSON Patch по стандарту RFC 6902.

Правило области видимости (API ядра): точка входа ядрового метода `apply_patch` принимает патчи, затрагивающие **только** пути данных (`/chunks/*`, `/spatial_index/*`, `/units/*`, `/profile/core_hints/relation_codes`, если профиль разрешает). Патчи в `/views/*` или `/profile/view_style_schema` являются клиентскими операциями профиля; они применяются и регистрируются через менеджер представлений/тем, а **не** через эндпоинт мутации данных ядра — именно для того, чтобы они не могли вызывать OCC-конфликты на уровне данных.

### 7.1 Каскадное удаление

При удалении узла ядро выполняет детерминированный обход потомков `parent_id` в глубину (сначала дети), удаляя всех транзитивных детей перед родителем. Если файл чанка после удаления оказывается полностью пустым, он физически удаляется из ZIP, а его запись удаляется из `manifest.chunks` и `manifest.spatial_index`; `global_version` инкрементируется; `state_hash` пересчитывается.

---

## 8. Слой представлений (View Layer): Только механизм

Стандарт контейнера определяет **механизм** тем оформления представлений (размещение файлов, регистрация в манифесте, трехуровневый порядок разрешения, семантика поверхностного слияния (shallow merge) по полям). Он **не** определяет, какие ключи находятся внутри правила стиля или каковы допустимые значения любого перечисления стилей.

### 8.1 Механизм разрешения — Трехуровневое поверхностное слияние по ключам

Каждый JSON темы в `views/` обязан содержать следующие ключи структуры верхнего уровня (из `schemas/view-theme.json`): `theme_id`, `theme_name`, `spec_version`. Дополнительно он объявляет ноль или более из: `fallback`, `by_type`, `by_id`.

Когда рендерер разрешает стиль узла, он выполняет следующие шаги:

```
         Наивысший приоритет
               ▼
         ┌─────────────┐
         │   by_id     │   Поиск по точной строке node_id.
         └──────┬──────┘
                │  ключ отсутствует? спуск ниже
                ▼
         ┌─────────────┐
         │   by_type   │   Поиск по дискриминатору, извлеченному с 
         └──────┬──────┘   помощью пути manifest.profile.view_type_key.
                │  ключ отсутствует? спуск ниже
                ▼
         ┌─────────────┐
         │  fallback   │   Значения по умолчанию для всей темы.
         └──────┬──────┘
                │  ключ отсутствует? спуск ниже
                ▼
         Жестко заданные финальные дефолты самого рендерера.

```

Слияние является **поверхностным и поключевым**: если правило более высокого приоритета определяет ключ K, оно побеждает; если оно опускает ключ K, используется значение из следующего уровня. Рендереры НЕ ДОЛЖНЫ заменять весь объект правила более низкого уровня целиком (что привело бы к потере неуказанных, но значимых унаследованных ключей).

### 8.2 Ключи внутри объекта правила стиля — на 100% принадлежат профилю

Имена, типы и семантика отдельных ключей внутри `by_type[*]`, `by_id[*]`, и `fallback` полностью определяются `manifest.profile.view_style_schema`. Слой контейнера не ограничивает и не перечисляет их в данном документе. Примеры, которые может определить профиль (не нормативные — исключительно иллюстративные):

* профиль `arch_floorplan_v2` может определять `{stroke_color_hex, line_dash_code, hatch_ordinal, label_text_path, label_anchor_ordinal}`
* профиль `pcb_oenull_v1` может определять `{pad_mask_layer, copper_net_class_code, silk_opacity, drill_plating_bit}`
* профиль `network_topology_v4` может определять `{bg_gradient_id, stroke_net_color, icon_glyph_id, tooltip_path_expression}`

### 8.3 Эталонный скелет темы (только механизм)

Минимальный скелет `views/default_theme.json` поставляется с эталонной реализацией исключительно для демонстрации формы трехуровневой структуры. Ключи правил стиля в нем являются лишь заполнителями; реальный профиль заменяет их настоящими контрактами, определенными в профиле.
